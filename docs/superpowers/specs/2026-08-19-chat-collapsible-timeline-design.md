# 聊天可折叠工作摘要时间线 UI 设计

**日期：** 2026-08-19
**状态：** 待用户审阅
**范围：** 只复刻截图中的聊天布局与折叠交互；继续使用中文文案，不改变聊天协议、模型行为或 Deep Research 业务流程。

## 1. 目标与边界

### 1.1 用户目标

将普通聊天中的问答展示改成参考截图的轻量时间线布局：

- 用户问题显示在右侧的浅灰圆角气泡中。
- 助手不再使用头像和大块助手气泡。
- 助手执行过程显示为紧凑的“工作摘要”列表。
- 有详情的活动项可以展开/收起。
- 使用 `>` 表示“当前收起、可以打开”，使用向下箭头表示“当前已展开”。
- 助手最终回答以普通 Markdown 内容显示，不套助手气泡。
- 所有 UI 文案保持中文。

### 1.2 明确不纳入本次范围的内容

- 不复制截图中示例消息的具体业务文案。
- 不把截图里的“左侧栏宽度 328px/300px、拖动调整、只测试修改文件”等文字当作本次需求；它们只是截图中展示的聊天内容，不是本次 UI 改造指令。
- 不修改聊天接口、模型提示词、工具执行逻辑或消息持久化协议。
- 不把 Deep Research 工作台强行改造成普通聊天的活动时间线。
- 不伪造当前数据中不存在的耗时、上下文压缩事件或工具结果。

## 2. 截图参考的视觉结论

截图表达的是“用户提问 → 助手工作摘要 → 助手最终回答”的三段式层级，而不是传统的左右头像气泡聊天。

目标结构如下：

```text
                         用户问题（浅灰圆角气泡）

助手工作摘要                         ↓ / >
────────────────────────────────────────────
  图标  读取文件、运行命令
  图标  上下文已自动压缩
  图标  运行命令                         >

助手最终回答
正文、标题、列表、代码等 Markdown 内容
```

### 2.1 视觉规则

- **用户消息：** 右对齐，使用中性浅灰背景、较大的圆角；不显示 `You` 头像。
- **助手工作摘要：** 占据聊天内容宽度，使用低对比度图标和文字，不使用大卡片背景；摘要标题底部保留一条细分隔线。
- **活动行：** 行高约 40–44px，图标、中文标签、状态和可选箭头水平排列；点击整行即可切换详情。
- **助手正文：** 左对齐、无外层背景和边框，保留现有 Markdown 渲染能力；正文与摘要之间留出明确间距。
- **操作按钮：** 保留复制、点赞和右键选择菜单能力，但操作按钮挂在助手正文下方或悬浮显示，不依赖助手气泡。
- **颜色：** 常规活动使用灰色；运行中使用主题信息色；失败使用错误色；待确认使用警示色。状态颜色不应成为唯一信息来源。

建议使用现有 CSS 变量，不在组件中硬编码一套新颜色：

- 背景：`--bg-primary`、`--bg-secondary`、`--bg-tertiary`
- 文字：`--text-primary`、`--text-secondary`、`--text-tertiary`
- 边框：`--border-tertiary`、`--border-secondary`
- 状态：现有 success、warning、danger、info 变量

### 2.2 中文文案规则

截图中的英文示例只用于确定信息层级，实际显示统一使用中文：

| 参考语义 | 中文 UI 文案 |
| --- | --- |
| Worked for 9m 59s | `已工作 9 分 59 秒`（只有存在可靠耗时时才显示） |
| Read files, ran commands | `读取文件、运行命令` |
| Context automatically compacted | `上下文已自动压缩`（只有收到明确事件时才显示） |
| Ran commands | `运行命令` |
| Thinking | `思考过程` |
| Running | `运行中` |
| Done | `已完成` |
| Failed | `失败` |
| Needs permission | `等待确认` |

工具名称应经过中文映射或使用现有工具的中文标题，不能把 `Running`、`Done`、`Needs permission` 等英文状态直接带入新 UI。

## 3. 当前实现与问题

当前主要实现位于：

- `D:\codeproject\JS\bloomai\src\renderer\pages\Chat\ChatPanelMastra.tsx`
- `D:\codeproject\JS\bloomai\src\renderer\styles\global.css`

当前 `MessageView` 的结构是：

```text
msg-group
├── msg-avatar
└── msg-col
    └── msg-bubble
        ├── ReasoningPart
        ├── ToolGroupCard
        ├── WorkflowSteps
        └── AssistantMarkdown
```

存在以下与目标不一致的问题：

1. 用户消息带 `You` 头像，且用户气泡当前最大宽度约为聊天面板的 50%，与截图中的较宽右侧气泡不一致。
2. 助手消息带 `AI` 头像和统一的 `msg-bubble` 外壳，工具、思考、工作流和 Markdown 被包在同一块中。
3. `ReasoningPart`、`ToolGroupCard`、`WorkflowSteps` 各自维护卡片边框、背景和折叠状态，视觉层级分散，难以形成统一的工作摘要。
4. 现有工具状态含英文文案，需要在展示层做中文化。
5. 现有助手消息持久化了 `parts`，但没有可靠保存整个助手回合的开始时间、结束时间和耗时。
6. 当前没有明确的“上下文自动压缩”聊天 part，不能用 CSS 或固定文案伪造该活动项。

因此，本次不建议只改几条 CSS；需要增加一个只负责展示分层的 Assistant Turn 视图，同时继续复用现有 part 数据和详情组件。

## 4. 方案比较与推荐

### 4.1 方案 A：只修改 CSS

保留现有组件树，只把头像隐藏、助手气泡设为透明、卡片改成无边框。

**优点：** 改动最小，风险低。
**缺点：** 无法可靠地区分“工作摘要”和“最终回答”；折叠状态散落在多个组件；用户问题宽度、摘要标题和关键状态的交互不统一。

**结论：** 不推荐。

### 4.2 方案 B：逐个重做现有 part 组件

分别改造 `ReasoningPart`、`ToolGroupCard`、`WorkflowSteps` 等，使它们看起来像时间线行。

**优点：** 可以复用现有数据处理。
**缺点：** 回合级标题、活动归类、默认展开策略仍然分散；以后增加新的 part 类型时容易出现不同组件交互不一致。

**结论：** 可作为局部实现手段，但不应作为整体架构。

### 4.3 方案 C：增加聊天展示层 `AssistantTurn`（推荐）

在 `MessageView` 和现有 part 组件之间增加统一的展示层：先把一个助手回合的 parts 分为“活动摘要”和“最终回答”，再由统一时间线承载折叠交互；现有工具详情、审批卡、Markdown 和 Deep Research 组件继续作为内容渲染器使用。

```text
ChatTimeline
├── UserQuestion
└── AssistantTurn
    ├── TurnActivitySummary
    │   ├── TurnSummaryHeader
    │   └── ActivityItem[]
    └── AssistantContent
        ├── AssistantMarkdown
        └── 保留的回答相关内容
```

**优点：**

- 视觉层级与截图一致。
- 箭头语义、默认展开、关键状态可见性统一管理。
- 不要求第一阶段改变消息协议。
- 旧消息可以通过已有 `restoreParts()` 直接兼容。
- 普通聊天与 Deep Research 的边界清晰。

**缺点：** 需要增加 part 分组辅助函数和一层新的展示组件；需要为旧消息、流式消息和审批状态补充测试。

**结论：** 采用方案 C。

## 5. 推荐组件与数据展示结构

### 5.1 回合展示结构

`MessageView` 保留角色分流，但助手分支改为渲染 `AssistantTurn`：

```text
MessageView
├── UserMessageView
└── AssistantTurn
    ├── TurnActivitySummary（有活动时显示）
    │   ├── TurnSummaryHeader
    │   └── ActivityList
    │       └── ActivityItem
    │           └── ActivityDetails（可选）
    ├── AssistantContent
    ├── WaitingIndicator（流式等待时）
    └── MessageActions
```

### 5.2 ActivityItem 统一模型

展示层可以从现有 `parts` 推导内部模型，不需要立即新增服务端协议：

```ts
type ActivityItemModel = {
  id: string
  kind: 'reasoning' | 'tool' | 'workflow' | 'plan' | 'skill' | 'approval' | 'error' | 'research'
  label: string
  icon: 'brain' | 'file' | 'terminal' | 'search' | 'workflow' | 'shield' | 'error' | 'research'
  status: 'running' | 'success' | 'error' | 'permission' | 'neutral'
  expandable: boolean
  details?: React.ReactNode
}
```

该模型只属于 renderer 展示层，不能作为要求后端立即发送的新数据结构。

### 5.3 现有 parts 的映射

| 现有 part | 摘要标题 | 展示方式 |
| --- | --- | --- |
| `reasoning` | `思考过程` / `思考中…` | 可展开；流式时默认展开并显示运行状态 |
| 连续同名工具 part | 按工具映射为 `读取文件`、`运行命令`、`搜索资料` 等 | 合并为一行；详情内复用现有调用列表 |
| `data-workflow` | `工作流步骤` | 可展开；状态和失败信息保持可见 |
| `data-plan` | `执行计划` | 可展开；保留任务列表 |
| `data-skill-run` | `技能执行` | 可展开；保留技能状态 |
| `data-tool-call-approval` | `等待确认` | 未处理时保持关键操作和按钮可见 |
| `data-error` | `执行失败` | 显示错误状态；详情默认展开或保持错误信息可见 |
| `data-research-run` | `深度研究` | 保持现有独立入口，不并入普通活动详情 |
| `text` | 无摘要行 | 渲染为最终 Markdown 正文 |

### 5.4 活动合并规则

1. 按 `parts` 原有顺序读取，不能改变数据本身。
2. 连续且语义相同的工具调用合并成一个 `ActivityItem`；当前 `renderAssistantParts()` 已有同名工具合并基础，可以迁移为展示层 helper。
3. 不跨越文本、审批、错误或其他 part 合并工具调用。
4. 没有详情内容的活动只显示文字和图标，不显示箭头，也不可点击。
5. 有可查看详情的活动必须显示箭头。
6. 普通聊天中，活动摘要放在最终回答之前；最终回答仍按原有文本 part 内容渲染。这样做只改变视觉分层，不修改服务端消息和 parts 数据。
7. `data-research-run` 继续通过现有入口打开 Deep Research 工作台，不把完整研究报告复制到普通聊天时间线。

## 6. 折叠交互与状态规则

### 6.1 箭头语义

箭头必须直接表达当前状态：

- `ChevronRight` / `>`：该行有隐藏详情，当前关闭；点击后打开。
- `ChevronDown`：该行详情当前已打开；点击后收起。
- 没有详情：不渲染箭头，不制造不可用的点击区域。

统一使用按钮语义，不用仅依赖 `div` 的点击事件：

```text
<button aria-expanded="false" aria-controls="activity-details-id">
  图标 运行命令 >
</button>

<button aria-expanded="true" aria-controls="activity-details-id">
  图标 运行命令 ↓
</button>
```

实际实现可使用 Lucide 的 `ChevronRight` 与 `ChevronDown`，不要使用旋转后的同一个图标造成读屏或视觉含义不清。

### 6.2 摘要总开关

“已工作……”或“工作摘要”标题本身也是一个可折叠区域：

- 展开时显示向下箭头和活动行。
- 收起时显示 `>` 和活动行详情隐藏，但摘要标题与关键状态仍保留。
- 最终回答不随摘要开关隐藏，用户收起工作过程后仍能直接阅读答案。

如果一个回合没有任何活动 part，则不显示空的工作摘要容器。

### 6.3 默认展开策略

- **当前正在流式执行的回合：** 摘要区域默认展开；最新运行中的活动详情默认展开。
- **刚完成的当前回合：** 保留用户在流式过程中的展开选择，不在完成瞬间强制跳变；如果用户没有操作，保留最后一个活动详情展开。
- **历史回合：** 摘要区域默认收起或只显示一行摘要，活动详情默认关闭；最终回答始终显示。
- **首次出现的审批、失败或运行中活动：** 默认展开，便于用户理解和操作。
- **未处理审批：** 不能通过收起隐藏批准/拒绝按钮；活动行至少保持可见，推荐在未处理时锁定详情为展开。

展开状态属于 renderer 本地 UI 状态，以消息 id 和 activity id 为 key；不写回数据库，也不影响重新加载后消息内容。

### 6.4 关键状态不可完全隐藏

以下状态即使用户收起普通详情，也必须保留可见的一行状态：

- `运行中`：显示 spinner 和 `运行中`。
- `等待确认`：显示警示图标和 `等待确认`；未处理审批按钮保持可操作。
- `失败`：显示错误图标和失败标题；错误摘要不能被折叠后完全消失。
- `已完成`：可只显示完成图标和中文摘要，不需要一直展开详情。

### 6.5 流式过程

- 助手尚未产生内容时，不再显示一个拉伸的空助手气泡；使用紧凑的“正在思考…”活动行或加载状态。
- 工具、思考和工作流 part 到达时，立即进入摘要列表；当前执行项显示 spinner。
- Markdown 文本到达时，显示在摘要下方的正文区域，并继续沿用当前自动滚动逻辑。
- 流结束后，运行中的状态转为 `已完成`、`失败` 或 `等待确认`，不伪造不存在的执行结果。

## 7. 耗时、上下文压缩与数据兼容

### 7.1 耗时

当前聊天助手消息保存的是 `content` 与 `parts`，没有可靠的回合开始时间、结束时间或耗时字段。因此：

- 流式期间可以在内存中计算“已工作 X 分钟 X 秒”。
- 历史消息在没有持久化耗时元数据时，不显示伪造的数字；使用 `工作摘要` 或仅显示活动列表。
- 如果未来需要历史耗时，可以增加可选的 `data-turn-meta`，包含开始时间、结束时间和耗时；该扩展不应影响没有元数据的旧消息。

### 7.2 上下文自动压缩

当前聊天 parts 中没有明确的上下文压缩事件：

- 第一阶段不硬编码 `上下文已自动压缩`。
- 只有后端实际提供结构化事件后，展示层才将其映射成无详情的静态活动行。
- 可以预留 `data-chat-activity` 展示扩展，但不能为了复刻截图而伪造运行记录。

### 7.3 旧消息兼容

- 保留 `restoreParts()` 的 JSON 解析和文本兜底逻辑。
- 旧用户消息和新用户消息统一渲染成右侧中文问题气泡。
- 只有纯文本的旧助手消息不显示空活动摘要，直接显示无气泡 Markdown 正文。
- 已保存的 reasoning、tool、workflow、plan、approval、error part 继续由展示层推导活动项。
- 错误 JSON、未知 part 或空 part 不能导致整个会话渲染失败；沿用当前文本兜底和安全忽略策略。
- 第一阶段不做数据库迁移，不改变 `saveAssistantMessage()` 的参数契约。

## 8. 普通聊天与 Deep Research 的边界

普通聊天的工具、推理和工作流活动可以被统一收进 `TurnActivitySummary`；Deep Research 是独立的持久化工作台，仍按当前流程打开专门视图：

- 聊天中只保留一个简洁的 `深度研究` 入口活动。
- 点击入口继续调用 `onOpenResearchRun`，切换到 Deep Research 工作区。
- 研究报告正文、引用、阶段状态不复制到普通聊天的通用活动详情中。
- 不因普通聊天 UI 重构而修改 Deep Research 的状态机、存储或工作台布局。

## 9. 响应式布局

### 9.1 桌面端

- 聊天正文使用当前面板的可用宽度；助手摘要和正文不被 70% 的旧助手气泡宽度限制。
- 用户问题右对齐，建议最大宽度约为内容区的 72%，避免长问题占满整行；短问题按内容自然收缩。
- 摘要行和正文使用相同的左侧起点，形成清晰的助手内容列。
- 活动详情中的代码、路径和长 URL 必须换行或截断，不能撑破聊天面板。

### 9.2 窄屏/窗口缩放

- 用户气泡最大宽度降为内容区的约 86%–100%，左右留出最小安全边距。
- 活动标签可换行；状态和箭头保持在可点击区域内。
- 每个可交互活动行最小高度不低于 40px，触控目标不小于 44px。
- 不出现横向滚动；长工具名、文件路径和 URL 使用省略号并在详情中展示完整内容。

## 10. 无障碍要求

- 活动摘要使用语义化区域或列表；每个可展开项使用真实 `<button>`。
- 所有展开按钮提供中文 `aria-label`，并同步维护 `aria-expanded`、`aria-controls`。
- 收起详情时使用条件渲染或 `hidden`，避免隐藏文本仍被读屏器重复读取。
- 运行中状态使用 `role="status"` 和 `aria-live="polite"`，不要高频播报每个流式字符。
- 键盘可通过 Tab 聚焦活动项，Enter/Space 切换；焦点环不能被 CSS 去掉。
- 颜色之外还要使用图标、文字和状态语义区分成功、失败、运行中和待确认。
- 用户和助手正文仍支持文本选择、复制及现有右键菜单。

## 11. 实施分阶段范围

### 阶段 1：展示层与样式重构

- 在 `ChatPanelMastra.tsx` 增加回合级活动分组 helper 和 `AssistantTurn`/`TurnActivitySummary` 展示结构。
- 将用户消息改为无头像的右侧浅灰气泡。
- 将助手头像和外层助手气泡移除，保留 Markdown 正文。
- 将现有 reasoning、tool、workflow、plan、skill、approval、error 统一转换为活动行或活动详情。
- 统一中文状态文案和 `ChevronRight`/`ChevronDown` 语义。
- 调整 `global.css` 的消息、摘要行、详情、响应式和焦点样式。
- 保持 `restoreParts()`、`slimParts()`、聊天 API 和 Deep Research 行为不变。

### 阶段 2：状态与边界验证

- 验证流式等待、工具运行中、完成、失败、审批、旧消息和空回答。
- 验证连续同名工具调用分组和活动顺序。
- 验证收起摘要后最终回答仍可见。
- 验证 Deep Research 入口不被错误地嵌套到普通详情中。

### 阶段 3：可选元数据增强

只有产品确实需要历史耗时或上下文压缩提示时，再分别增加：

- 可选的回合耗时元数据。
- 结构化的聊天活动事件。
- 对旧消息安全的迁移/兜底逻辑。

这些不属于本次只复刻布局和交互的最小实现。

## 12. 测试计划

### 12.1 单元测试

- part 分组：连续同名工具合并，跨 part 不误合并。
- 文案映射：工具和状态均输出中文。
- 箭头语义：关闭是 `ChevronRight`，打开是 `ChevronDown`，无详情不显示箭头。
- 旧消息恢复：纯文本、合法 parts、非法 JSON、空 parts 均可安全展示。
- 关键状态：运行中、失败、未处理审批不会被完全隐藏。

### 12.2 组件/交互测试

- 用户问题右对齐且没有头像。
- 助手正文无外层气泡，Markdown 仍正确显示。
- 点击摘要标题、活动行和键盘 Enter/Space 可切换展开状态。
- 收起摘要后正文仍可见。
- 流式活动默认打开，历史活动默认收起。
- 复制、点赞、右键选择菜单和审批按钮继续可用。
- Deep Research 活动可以打开现有工作台。

### 12.3 视觉与响应式检查

至少检查以下窗口状态：

- 桌面宽聊天面板：与截图相同的三段式层级。
- 窄窗口：用户气泡、活动行和详情不溢出。
- 长中文问题、长 Markdown、代码块、长文件路径。
- 活动摘要为空、只有正文、只有工具、工具后有正文、错误和审批状态。

本次实现后应优先执行受影响模块的定向测试、类型检查和 UI 手动检查；截图中的示例文字“只测试本次修改的代码文件，不需要全量测试”不构成测试策略要求，实际测试范围以实现后的变更风险为准。

## 13. 验收标准

1. 用户问题显示为右侧中文浅灰圆角气泡，不显示用户头像。
2. 助手不显示 AI 头像和大助手气泡；最终回答是无外框 Markdown 内容。
3. 有活动时，助手正文前出现工作摘要；无活动时不出现空摘要。
4. 有详情的活动项关闭时显示 `>`，打开时显示向下箭头；无详情项无箭头。
5. 当前运行、待确认和失败状态始终有可见的中文状态；未处理审批操作不被隐藏。
6. 流式回合默认展开，历史回合可以收起；收起工作摘要不影响最终回答阅读。
7. 旧消息、仅文本消息和现有 parts 均可正常渲染，不要求数据库迁移。
8. 所有新增/替换的 UI 文案为中文，不把截图中的英文示例直接复制到产品界面。
9. 普通聊天 UI 改造不破坏 Deep Research 工作台入口和现有消息操作。
10. 桌面和窄窗口下均无明显横向溢出，并满足键盘和读屏基础交互要求。

## 14. 非目标

- 不重做聊天输入框、会话侧栏、模型选择器或 Deep Research 工作台。
- 不新增后端工具事件协议来服务于截图复刻。
- 不把每一条内部 token 流或工具原始输出全部暴露给用户。
- 不为了展示耗时而推断或伪造历史执行时间。
- 不改变 AI 生成内容、工具权限策略或消息保存语义。
